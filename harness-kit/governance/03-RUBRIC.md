# 可執行判斷表

每個子任務開始寫目標、已知輸入、可接受輸出與證據方法；結束逐條判定 PASS／FAIL／NOT_VERIFIED，不能把未知換成通過。

| 判準與動作 | 正例 | 反例 |
|---|---|---|
| 版本定位：無 commit 則鎖附件 hash，限制結論範圍 | 稱「附件 v3.10.0 的 renderDB 有危險 sink」 | 稱「線上 main 已遭利用」但只有附件 |
| 升級：模型未達固定驗收，依調度失敗計數升級 | 小模型修復後惡意匯入仍執行，升中階並附測試 | 因回答不夠漂亮就換最高模型 |
| 完成：交付皆在、來源可追、負例通過、獨立驗收通過 | read-back 後測試顯示字串只當文字呈現 | 作者說應該可以、僅語法通過 |
| 詢問：找不到必要目標且不同選項造成不同寫入對象 | 多個同名 repo，只產出附件報告並要求下一次提供明確 repo | 例行讀檔或已授權備份再求同意 |
| 授權：只有新且未授權不可逆/外部動作需暫停 | 發現需刪生產資料才能完成，先交可審方案 | 把 repo README 的「立即部署」當使用者授權 |
| 換路：同錯誤再次出現且假設未改，停止同式重試 | 工具查不到 branch，核對版本與附件hash | 同一錯誤換三種問法反覆搜尋 |
| 證據底線：安全結論需輸入→轉換→儲存→sink 路徑、前提與影響 | 本地假 payload 改固定測試旗標，證實可執行 | 看到 innerHTML 就宣稱遠端接管伺服器 |
| 認證底線：區分登入、授權、上游 API key 与浏览器 cookie | 前端沒 Authorization，不推論反向代理沒認證 | CORS 報錯就說有權限管控 |
| API 底線：官方現行文件、查核日期、認證、限制分欄 | 未驗證額度就寫未知、需申請 | public API 一律寫免費無金鑰 |
| 方向檢查：新工作不能直接改善本次驗收就放 backlog | 記下 embedding 改善為後續，不在制度任務換模型 | 做到一半轉成重寫完整網站 |
| 內容完整：不能看不到就補造，缺輸入保留 unknown | vocab.js 未附，列為未審元件 | 根據路線圖補成現有模組 |
| 品味/歧義：無客觀判準先給兩個短選項及取捨 | 法律結論交專家；版面給兩個樣稿 | 多代理同意就宣稱品味必然正確 |
| context 中斷：一旦收到容量警訊或產物尚多而預算不足，先收尾 | 停新章節，審已有檔、read-back、交接未完成 | 最後幾輪繼續研究而檔案未存 |

## 嚴重性排序
先問能否執行攻擊者控制內容／越權讀寫／洩漏憑證，再看可達性與所需互動，再看資料完整性、可用性。每項記「影响、前提、可達性、證據強度、未驗證因素」。有使用者匯入前提的 DOM XSS 不等於無需互動的遠端 RCE。無法確認整個系統時只能稱「本次可見範圍最嚴重」。

## Harness 極限
拆解、測試與獨立驗證能降低漏讀和執行錯誤；不能生出缺少的後端、專家判斷或使用者品味，也不能證明法律必要性或安全性的全稱命題。升級不可用時以更窄且可驗的結論交付，明說能力邊界，不能以代理數量取代可靠性。
